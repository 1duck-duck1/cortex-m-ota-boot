# 00 项目规划总览

> 本文是项目的顶层规划：定位、功能范围、里程碑、开源运营。
> 架构设计见 `01-architecture.md`，Git 与 GitHub 操作见 `02-git-and-github.md`。

---

## 1. 项目定位

### 一句话定位

> 面向 Cortex-M3/M4 的可移植 A/B 双分区 OTA Bootloader，同一套核心逻辑经 STM32F103 与 STM32F407 两块真实板子验证，支持掉电安全回滚。

这句话直接作为 GitHub 仓库 README 的第一行。

### 关键差异点（为什么别人要用你的而不是别家的）

| # | 差异点 | 竞品现状 |
|---|---|---|
| D-1 | 可移植性由**两块真实板子的移植过程验证**，而非口头声明 | 大多数项目只在一款芯片上跑通 |
| D-2 | 核心逻辑 `core/` 与硬件完全解耦，**可在 PC 上单元测试** | 几乎没有同类项目做 |
| D-3 | 掉电安全：不仅声称支持，还提供**可复现的断电测试数据** | 绝大多数项目只写"支持掉电恢复" |
| D-4 | 明确的移植契约：1 个头文件 + 8 个函数 + 一份分区布局 | 移植说明含糊或不存在 |

### 目标用户

1. 需要给 Cortex-M 产品加 OTA 能力但不想自己造的嵌入式工程师；
2. 想学习 Bootloader / 固件升级实现原理的学生与初学者；
3. 需要把 OTA 方案移植到自家芯片的团队。

### 验证标准（定位是否成立）

> 一个陌生人 clone 仓库后，**能照着 README 在一次会话内完成一次真实升级**。

做不到这一点，定位就是失败的，优先修 README 和 Quick Start，而不是加功能。

## 2. 技术选型（已确定）

| 项 | 选择 | 说明 |
|---|---|---|
| 硬件平台 | STM32F103（M3）+ STM32F407（M4） | F1 均匀 page、F4 不均 sector，差异正好验证抽象 |
| 升级传输 | UART + YMODEM | 后续扩展 CAN |
| 安全特性 | v0.5 之后引入 | 第一版不加密、不签名 |
| 语言 | C99（core 层） + Python（上位机/工具链） | core 层零依赖 |
| 构建 | CMake + arm-none-eabi-gcc + Ninja | 保证 Linux/CI 可编译 |
| 辅助工程 | 提供 Keil / IAR 工程文件作为补充 | 不作为主工程 |

**为什么主工程必须是 CMake**：Keil 工程在 Linux 与 GitHub Actions 上完全无法编译，别人 clone 后第一步就会卡住。Keil 工程只能作为"顺手的附件"存在。

## 3. 功能清单

功能编号（F-xx / X-xx / N-xx）后续直接用作 GitHub Issue 标题前缀，便于追踪。

### 3.1 核心功能（必做，v1.0 前完成）

**启动与跳转**

- **F-01 应用有效性校验**：上电读取激活槽的固件头，校验 magic / CRC / HW ID，无效则停留在 Bootloader。
- **F-02 应用跳转**：关中断、清 NVIC pending、反初始化外设、设置 `SCB->VTOR`、从 App 向量表取 MSP 与 Reset_Handler 并跳转。
- **F-03 反向跳转**：App 通过备份寄存器（BKP）或保留 RAM 标志请求进入 Bootloader，实现"应用触发升级"。
- **F-04 应用回跳保护**：防止 App 反复重启导致 Bootloader 无限循环。

**传输与协议**

- **F-05 传输抽象层**：`transport` 接口（open / read / write / close / timeout），v1.0 只实现 UART。
- **F-06 YMODEM 接收**：实现 128/1024 字节包、CRC16 校验、重传与超时处理。
- **F-07 备用自定义帧协议**：为后续 CAN 等非流式通道预留的定长帧协议（v1.0 可不含）。

**固件与元数据**

- **F-08 固件头解析**：magic / header_ver / hw_id / fw_version / image_size / crc32 / header_crc32。
- **F-09 固件合法性校验**：头部 CRC → 载荷 CRC → HW ID 匹配 → 目标槽容量匹配。
- **F-10 元数据双副本管理**：带序号 + CRC 的两份记录轮换写，保证任意时刻至少一份有效。
- **F-11 升级状态机**：IDLE / RECEIVING / VERIFIED / PENDING_TEST / CONFIRMED / ROLLBACK。
- **F-12 A/B 分区切换**：更新元数据中的激活槽，不改动固件本体。

**可靠性与安全**

- **F-13 掉电安全**：接收过程中断电，重新上电可重新发起升级，旧固件不受影响（因为写入的是非激活槽）。
- **F-14 启动失败自动回滚**：新固件处于 PENDING_TEST 时若连续启动尝试超过阈值（默认 3 次）仍未确认，自动切回旧槽。
- **F-15 应用侧确认接口**：`boot_confirm()` 供 App 在自检通过后调用，将状态置为 CONFIRMED。
- **F-16 自身分区写保护**：拒绝任何擦写 Bootloader 区与元数据区的越界请求。

**工具与交付**

- **F-17 固件打包工具**：Python 脚本，为 `.bin` 追加固件头，输出 `.pkg`。
- **F-18 上位机升级工具**：Python，跨平台，`pip install` 可装，一条命令完成升级。
- **F-19 串口命令行**：查询版本、槽状态、强制进入升级、擦除指定槽、手工确认。
- **F-20 移植契约与移植指南**：`port/port.h` + `docs/移植指南.md`。
- **F-21 PC 端单元测试**：mock port（用 RAM 数组模拟 Flash），测试 core 层状态机与掉电恢复。

### 3.2 加分功能（v0.5 之后，按需实现）

| 编号 | 功能 | 说明 |
|---|---|---|
| X-01 | Ed25519 签名校验 | 固件头追加签名域，公钥内置 |
| X-02 | 防回滚 | 固件版本单调递增，拒绝降级 |
| X-03 | 固件加密 | AES-CTR 解密后校验 |
| X-04 | CAN 传输 | 基于 F-07 帧协议 |
| X-05 | 双 Bank 无搬运升级 | 针对 F42x/F43x 等双 Bank 型号，体验最优 |
| X-06 | Factory / Recovery 救援固件 | 三级兜底 |
| X-07 | 掉电测试台 | 继电器或可编程电源 + 脚本，自动化随机断电测试 |
| X-08 | QEMU / 仿真器支持 | 无需硬件即可跑通流程 |

### 3.3 明确不做（写进 README，防止范围蔓延）

| 编号 | 不做的事 | 原因 |
|---|---|---|
| N-01 | Bootloader 自更新 | 需要搬运自身，复杂度与变砖风险极高 |
| N-02 | 差分升级（bsdiff） | 版本管理复杂，收益在通用项目里不明显 |
| N-03 | 云平台 / 服务器端 | 超出项目边界 |
| N-04 | 图形化上位机 | 命令行 + Python 脚本足够 |
| N-05 | 全厂商芯片覆盖 | 只保证 F103 / F407 质量，其余靠社区贡献 |
| N-06 | RTOS 深度集成 | 只提供裸机与"RTOS 下可调用"的最小接口 |
| N-07 | 动态内存分配 | Bootloader 全程静态分配，这是硬约束 |

## 4. 里程碑路线图

每个版本都必须是**可独立发布、可被别人用起来**的状态。宁可版本号多，不要憋大招。

### v0.1.0 — 地基

- **目标**：Bootloader 能跳 App，App 能跳回 Bootloader。
- **交付**：F-01（简化版）、F-02、F-03、F-04、F-19（最小命令集）、仓库骨架、LICENSE、README。
- **验收**：F103 真板上双向跳转成功，串口能看到 Bootloader 打印。
- **纪律**：**允许写死、允许代码丑**，不引入任何抽象层。

### v0.2.0 — 能升级

- **目标**：手动完成一次完整升级。
- **交付**：F-08、F-09、F-17、F-18（最简字节流发送）、F-19（升级命令）。
- **验收**：串口发送 `.pkg`，写入非激活槽，校验通过后重启进入新固件。
- **此时的状态**：升级时断电会变砖（激活槽还没切换机制），这是已知的、可接受的。

### v0.3.0 — 掉电安全（项目质变点）

- **目标**：掉电任意时刻都能恢复。
- **交付**：F-10、F-11、F-12、F-13、F-14、F-15、F-16、F-21。
- **验收**：
  1. PC 端 mock 测试：模拟 500 次随机断电点，全部恢复到可启动状态；
  2. 真板拔电测试：随机时刻断电 100 次，全部恢复正常。
- **同时完成**：把硬件无关逻辑抠进 `core/`，此时才引入 `port` 分层。
- **纪律**：抠 `core` 的过程中如果发现抽象别扭，**重构抽象，不要打补丁**。

### v0.4.0 — 可移植性宣言（项目第二个质变点）

- **目标**：证明架构真的通用。
- **交付**：`port/stm32f4/` 实现、F-20 移植指南、F-21 补齐 F4 分区测试。
- **验收**：移植 F407 时**除 `port/stm32f4/` 外没有修改 `core/` 下任何文件**，且 F407 上完整升级 + 断电测试通过。
- **纪律**：这条验收标准是硬性的。违反了就回退重构，不许"临时在 core 里加个 if"。

### v0.5.0 — 安全

- **目标**：不可信固件无法运行。
- **交付**：X-01、X-02。
- **验收**：篡改 1 字节的固件被拒绝；低版本固件被拒绝。

### v0.6.0 — 好用

- **目标**：一行命令完成升级。
- **交付**：F-18 完善（pip 可装、进度显示、断点续传可选）、X-04（CAN）或 X-08（QEMU）二选一。
- **验收**：`pip install cortex-m-ota && ota flash --port COM3 firmware.pkg` 跑通。

### v1.0.0 — 稳定

- **目标**：接口冻结，可作为依赖使用。
- **交付**：`port.h` API 冻结并加版本宏、完整文档、`CHANGELOG.md`、示例工程、`docs/移植指南.md` 完善。
- **验收**：**第三方（非作者本人）能照文档成功移植到一款新芯片**。这是 v1.0 的唯一硬标准。

### 版本规划纪律

1. 每个版本打 tag 并写 GitHub Release，附上该版本的验收证据（截图 / 日志 / 视频）；
2. 任一版本在真实板子上跑不通，就**不发布**；
3. 新想法一律记成 Issue 并打 `later` 标签，不插队。

## 6. 风险与陷阱清单

| 风险 | 应对 |
|---|---|
| 抽象设计过早，做出空壳 | 铁律：F103 跑通前不写任何抽象层 |
| 范围蔓延，什么都想做 | 严格按第 3.3 节的"不做清单"执行 |
| F4 擦写时从 Flash 取指导致 HardFault | 擦写相关代码常驻 RAM（`BOOT_RAMFUNC`），见架构文档 |
| F4 sector 大小不均导致槽不等大 | 元数据记录各槽实际 size，打包时按 `min(A,B)` 校验 |
| 中断向量与 App 冲突 | 明确约定 Bootloader 用完的外设必须反初始化；App 自行重设 VTOR |
| 掉电测试难以复现 | 先做 PC 端 mock 测试取得可信数据，再上真实断电器 |
| 提交构建产物导致仓库膨胀 | `.gitignore` 严格配置，见 Git 指南 |
| 项目变砖劝退用户 | README 里明确"升级失败的恢复方法"，提供 SWD 恢复说明 |
